# Continuous Performance Implementation Plan

Status: implementation specification only. No application or harness code has been written for this plan.

**Goal**
Provide a local-first, automated browser performance loop: build the production game, execute repeatable workloads, detect regressions, automatically replay affected workloads under profilers, and report source-level evidence. CI runs the same commands as enforcement. Nightly runs exercise larger workloads and collect diagnostics even when measurements pass.

**Fixed Decisions**
These are implementation requirements, not options left to individual agents.

1. Use existing Playwright and Chromium/CDP. Add only `@jridgewell/trace-mapping` for source attribution. Use Node 24 native erasable TypeScript for the CLI and Vite+/Vitest for decorated browser/headless tests.
2. Keep the normal page and gameplay E2E boundary intact. A dedicated `performance.html` entry exposes visible benchmark controls and aggregate telemetry. Harness code may use browser timing APIs/CDP, but must never import `src`, inspect ECS/Pixi internals, or call hidden game methods.
3. Extract one shared runtime from `src/main.ts`. Both entries use the same systems, capped-dt update, HUD projection/update, render projection and Pixi render path. Normal builds do not bundle the benchmark entry; benchmark TypeScript is still type-checked.
4. Use a fresh page/context for every repetition and diagnostic replay. Do not implement live world/renderer reuse. Keep one browser worker, one active page and one workload at a time.
5. Every reported measurement has a mode: `clean`, `cpu-trace`, or `allocation`. Only clean measurements influence performance verdicts. CPU/trace and allocation passes never run simultaneously.
6. Store raw bounded samples and results even on failure. A timeout or missing metric is not zero. Distinguish performance regression, workload-invalid, unsupported capability, infrastructure failure, and unbaselined collection.
7. CLI commands: `vp run perf` measures the fast set and diagnoses failures; `vp run perf:diagnose --scenario <id>` forces CPU/trace evidence; `vp run perf:full` measures all scenarios and always runs CPU/trace plus the lifecycle allocation pass; `vp run perf:baseline --from <run-dir> --accept` explicitly accepts a valid local candidate. `--collect` is explicit unbaselined collection, never enforcing comparison.
8. `perf` and `perf:full` default to enforcing comparison. Without a compatible local baseline they still collect and report, then exit 2 with an exact collection/acceptance instruction. Absolute budget breaches still trigger diagnostics. `--collect` may exit 0 only when measurements/workloads and applicable absolute budgets pass; its status is `collected-unbaselined`, not `passed`.
9. Exit codes: 0 accepted or explicitly requested successful collection/diagnosis; 1 performance/capacity regression; 2 invalid inputs, workload, required baseline, or tooling. A known regression remains exit 1 if its diagnostic replay fails; record that failure separately. If the measurement cannot support a verdict, exit 2.
10. No automatic baseline acceptance. CI's accepted baseline is a reviewed tracked file. Successful current runs publish candidates/history but do not replace it. Local baseline compatibility includes machine identity; CI uses an explicit runner class plus detected environment. Build hash and commit identify provenance but must differ across comparable revisions.
11. Numerical workload sizes/durations below are initial specifications. Actual performance budgets are measured and approved in the calibration phase, not invented by an agent. Large synthetic tiers may have capacity-specific ceilings rather than a 60 FPS requirement; they still require valid sustained load and an enforced no-regression policy before completion.
12. Automated evidence means mapped CPU hot spots, observed rendering/GC events and navigable standard artifacts. It does not mean guaranteed root-cause identification, guaranteed replay reproduction, GPU-memory accounting or complete cross-process coverage.

**Phase 3: Workload Validity**

These are explicit workload definitions, not calibrated budgets.

Synthetic geometry is deliberately controlled: maintain foes in seeded ground-level slots across world x `[-160,160]`; retain health and allow real `FoeShamble`/collision/death to execute between maintenance callbacks. Maintain bolts in two cohorts: 80% visible upper-lane movers that scan foes but miss, 20% ground collision-lane movers that exercise hits/deaths. Upper lanes stay above the collision radius; recycle off-screen survivors and replenish expired/hit bolts. Use finite lifetimes and nonzero damage. Do not rely on zero damage/infinite lifetime to prevent hit destruction. Do not disable floor correction, AI or collision systems.
